# Ticket triage pipeline

A Python 3.11+ CLI that reads local JSON tickets, classifies each ticket with Claude Haiku 5.5 through OpenRouter, applies a fixed confidence threshold, and generates either a customer draft or an internal escalation note. Expected labels are used only for evaluation.

## Setup and run

Install the dependencies, preferably in a virtual environment:

```text
python -m pip install -r requirements.txt
```

The local `.env` is intentionally ignored by Git and initially contains a blank API key. From a clean checkout, copy `.env.example` to `.env`. Fill in `OPENROUTER_API_KEY` when ready to make real requests:

```dotenv
OPENROUTER_API_KEY=
CLASSIFICATION_MODEL=anthropic/claude-haiku-5.5
REPLY_MODEL=anthropic/claude-haiku-5.5
```

Run from the repository root:

```text
python main.py --tickets tickets.json --schema label_schema.json --output-dir outputs
python validate.py --tickets tickets.json --schema label_schema.json --output-dir outputs
python -m unittest discover -s tests
```

`python validate.py` also works with the default input and output paths. It does not need credentials or make network requests. Tests use a mocked HTTP transport and temporary directories, with no paid API calls.

The repository ships six sample tickets and a label schema. The pipeline accepts replacement files with the same structure and does not depend on the sample ticket IDs or ticket count. Generated artifacts are intentionally regenerated by execution, rather than committed as precomputed predictions.

To repeat a run, select another output directory or add `--overwrite`. Overwriting replaces the pipeline's known artifacts and starts a fresh call log; unrelated files and old, unreferenced raw response folders are retained. The validator checks the current run's references. Missing credentials or invalid inputs fail preflight before existing outputs are replaced.

Optional model overrides:

```text
python main.py --classification-model anthropic/claude-haiku-5.5 --reply-model anthropic/claude-haiku-5.5 --output-dir outputs
```

Model configuration precedence is CLI flags, environment variables, then defaults. Environment variables override values in `.env`, including an explicitly blank environment API key. Both stages default to Haiku 5.5; Jev is deferred because the assessment requires a model-generated explanation. Model overrides must support chat completions and JSON Schema output; there is no automatic fallback to another model.

## Input contract and preprocessing

`tickets.json` is an array of objects with these required fields:

```json
[
  {
    "ticket_id": "T1",
    "customer_message": "I cannot log in after resetting my password.",
    "expected_category": "login_access",
    "expected_urgency": "high"
  }
]
```

Ticket IDs must be unique nonempty strings, messages must be nonempty strings, and expected labels must belong to the supplied schema. Additional ticket fields are preserved in snapshots but excluded from prompts. Duplicate JSON keys, nonfinite numbers, and nesting deeper than 64 levels are rejected. An empty ticket array is supported.

`label_schema.json` supplies nonempty arrays of unique trimmed strings named `categories` and `urgency_levels`. It controls both the allowed labels in the prompt and the validation enums; labels are not hardcoded in the classifier. Standard urgency meanings are explained in the prompt, with instructions to use the supplied labels when they differ.

Preprocessing preserves every original message and adds `normalized_message`, which trims surrounding whitespace and converts CRLF/CR line endings to LF. It does not remove negations, lowercase text, or otherwise rewrite the message. Ticket order is preserved in all per-ticket output arrays. Expected labels never enter classification or reply prompts.

## Model output and routing

Classification uses a JSON-only prompt and requests this complete object:

```json
{
  "category": "billing",
  "urgency": "high",
  "confidence": 0.82,
  "reasoning_summary": "The customer reports missing funds.",
  "needs_human_review": false
}
```

The request uses `response_format.type=json_schema`, `strict=true`, dynamic label enums, and `provider.require_parameters=true`. Local validation still rejects missing/extra fields, invalid types, unknown labels, blank explanations, and invalid confidence. Confidence is a model estimate; this project does not claim independent calibration. See [OpenRouter structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs) and the [selected model](https://openrouter.ai/anthropic/claude-haiku-5.5).

If JSON is surrounded by text or Markdown, one recovery attempt extracts a single unambiguous JSON object. The same validation then runs. Multiple objects, invalid labels, and unrecoverable output are rejected; the code never guesses a correction. Recovery details and failures appear in parsed predictions and the error log.

Routing is deterministic:

| Classification | Route |
| --- | --- |
| Parsing, validation, or provider failure | `human_review` with an error reason |
| Valid confidence below `0.65` | `human_review` |
| Valid confidence at or above `0.65` | `auto_triage` |

The model's `needs_human_review` field is saved for audit and does not override the rule. Classification failures use null predicted labels and confidence `0.0` as an explicitly documented sentinel, rather than an invented schema label. Null predictions are accepted by validation only for recorded classification failures routed to review.

Auto-triaged tickets receive a second model call returning a `sentences` array. Validation requires 2-4 nonempty sentences, each ending in punctuation, and joins them into `customer_reply`. If the model puts several sentences into one array item, the recovery path splits the paragraph into individual sentences and revalidates the same 2-4 sentence limit. It preserves the words and normalizes whitespace; it never truncates extra sentences. Common abbreviations, initials, decimal numbers, and URLs are handled conservatively, but unusual prose may still require a retry. Recovery is recorded in reply predictions, the error log, and recovery metrics. The prompt requires acknowledgment, consistency with category and urgency, and no invented account facts, policies, or unsupported promises. These semantic constraints are prompt instructions, not a guarantee established by JSON validation; review raw drafts when assessing model quality.

Human-review tickets receive no reply call. Their `customer_reply` is null and their internal note is generated in code from the actual routing reason. These are saved drafts only; nothing is sent to customers.

## Required artifacts

The two inputs are shipped at the repository root. Every run also saves input snapshots alongside all six required generated outputs in the selected output directory:

| Required artifact | Contents |
| --- | --- |
| `tickets.json` | Input ticket snapshot |
| `label_schema.json` | Allowed-label snapshot |
| `preprocessed_tickets.json` | Original fields plus normalized message |
| `routing_decisions.json` | Ticket ID, route, confidence, routing reason |
| `triage_results.json` | Predicted labels, confidence, route, customer reply or internal note |
| `prediction_comparison.json` | Expected and predicted labels, correctness, status, route per ticket |
| `evaluation_report.json` | Accuracies, denominators, review count, failure and recovery counts |
| `llm_calls.jsonl` | One record per outbound model request, including retries and failures |

Additional audit and evaluation artifacts:

- `parsed_predictions.json`: validated classification objects or null predictions, status, errors, recovery details, and raw output references.
- `reply_predictions.json`: validated reply sentences or explicit failures for auto-triaged tickets.
- `raw_outputs/<run_id>/`: one JSON envelope per request with the actual request body and original response text, including malformed response text. Filenames use counters, so ticket IDs cannot become filesystem paths.
- `errors.json`: provider errors, parse/validation failures, and successful recovery events.
- `run_metadata.json`: run ID, timestamps, configured models, input hashes, and completion status.
- `confusion_summary.json`: category confusion matrix, most common mixups, and separately counted unclassified failures.

Each call log record contains `stage`, `ticket_id`, timezone-aware ISO-8601 `timestamp`, `provider`, requested `model`, `prompt_hash`, and relative `output_artifact`, plus the resolved model and upstream provider when supplied. The SHA-256 prompt hash covers a canonical serialization of messages and the output schema. Authentication headers are never saved; occurrences of the API key in response text are redacted. The raw artifact is written before its call-log record and before output parsing.

## Failure handling and evaluation

Requests time out after 60 seconds. Timeouts/transport errors, HTTP 429, and HTTP 5xx receive one retry after a one-second pause. Other HTTP errors and refused, truncated, or invalid provider envelopes are recorded without retry. Classification parse/validation failures route directly to review after the extraction recovery attempt. Invalid reply content receives one stricter retry; each reply-content attempt can independently receive a transport retry, for at most four reply HTTP requests in that worst case.

Ticket-level failures do not stop subsequent tickets. A final classification provider failure or a failed customer reply marks the run incomplete and returns a nonzero exit status. Classification parse/validation failures are normal escalations and can still produce a complete valid run. If an auto-triage reply fails, its confidence-based route remains unchanged, no reply is invented, and the validator rejects the incomplete run. Check the error and reply artifacts, then rerun after resolving the cause.

Category and urgency accuracy use every input ticket as their denominator; failed classifications count as incorrect. Correct low-confidence predictions still count as correct even when routed to review. Final classification parse/validation failures are counted per ticket, separately from provider failures, provider error attempts, reply failures, and successful recoveries. Empty input produces null accuracies with zero denominators.

Exit statuses:

- Pipeline `0`: completed and artifact validation passed.
- Pipeline `1`: incomplete run or artifact validation failed; available artifacts remain saved.
- Pipeline `2`: credential, input, output-directory, or filesystem error.
- Validator `0`: valid artifacts; `1`: missing, malformed, or inconsistent artifacts.

The validator checks all listed artifacts, exact ticket coverage and ordering, allowed labels, routing, replies and notes, raw-output/log references, prompt hashes and expected prompt contents, predictions against raw responses, and recomputed comparisons, metrics, and confusion counts. It does not certify the factual correctness of model classifications or drafts.

The offline tests exercise the real pipeline and HTTP adapter with mocked responses, including boundary confidence values, conflicting review suggestions, replacement schemas, malformed output, retries, missing credentials, empty input, failed replies, artifact tampering, and exclusion of expected labels from model inputs. A real API run requires filling the key and running the commands above.
